# 26.0.0-dev.2

Changes since `0.10.0`.

## New Features

### Driving the running app

- **`aimer input`**: sends a click, key or gesture to the app a run session launched, from a shell or a script. Subcommands include `click`, `move`, `drag`, `scroll`, `key`, `type`, a touch `tap`, and `send` for raw protocol lines.
    - It sends to the only live session; pass `--session <id>` (see `aimer sessions`) or `--project` when there are several.
- **MCP input tools**: `left_click`, `right_click`, `middle_click`, `double_click`, `triple_click`, `mouse_move`, `left_click_drag`, `scroll`, `key` and `type` drive the app like a mouse and keyboard, in the vocabulary of the computer-use tools. Coordinates are logical pixels from the top-left corner of the app's window.
    - The mouse glides along a curved, eased path instead of jumping, and a command sent mid-glide retargets it.
- **Screenshots**: `aimer screenshot` and the MCP `screenshot` tool take a picture of the app's window, as the app drew it, so an agent can see the result of what it did. By default a pixel in the picture is a logical pixel, so its coordinates can go straight into the click and scroll tools; `--width` and `--jpeg` make it smaller. The text that comes with the picture says what to divide by when it is scaled. Only macOS Metal apps can be captured so far; others say so at once.
- `scroll` is a smooth, trackpad-style swipe and takes an optional position (`--at X Y`); without one it scrolls wherever the mouse already is. `type` types a keystroke at a time at a human pace, so a screen recording looks driven by a hand.
- The click tools take an optional coordinate: without one the click happens where the mouse already is, once an earlier click, `mouse_move` or `scroll` has placed it. `aimer input click` takes an optional `X Y` too.
- The input tools are **listed only while an app is connected** to the session, not merely while the MCP server is attached to it. The server tells the client when the list changes, so they appear when the app connects and go when it exits.
- **Touch tools** `tap`, `swipe` and `pinch` for apps on a phone or tablet.
- **`send_input`**: sends raw `aimer_prendre` protocol lines for events the tools above do not cover, such as `back`, `link`, `menu`, `file-drop`, `preedit` and `quit`. The whole request is checked before anything is sent.
- `aimer run` now asks the app it launches to accept input, on macOS, desktop and iOS (Simulator and device). A debug build starts the input server; a release build never does. Nothing needs to change in the app.
    - On an iOS device the CLI reaches the app through the `devicectl` tunnel address, wired or wireless.
    - Set `AIMER_PRENDRE=0` for `aimer run` to turn it off.
    - Android is not wired yet.

### Permissions

- **`[permissions]` in `Aimer.toml`**: declare `camera`, `microphone`, `location`, `photos`, `contacts` and `internet` once. Assembling for macOS, iOS or Android writes them into `Info.plist` and `AndroidManifest.xml`. `[ios.permissions]`, `[macos.permissions]` and `[android.permissions]` take raw keys for anything else.
    - The generated entries sit between `aimer:permissions:start` and `aimer:permissions:end` comments and are rebuilt on every assemble. Everything outside them stays yours.
    - A hand-written `Info.plist` entry that `Aimer.toml` replaces is turned into a comment, not deleted, and the build says which key changed. See `docs/CONFIGURATION.md`.

### Live activities

- **Automatic iOS setup**: when `Cargo.toml` turns on the `live-activity` feature of `aimer` (or depends on `aimer_live_activity`), building for iOS writes the Swift bridge and attributes into the app, adds a live-activity-only widget extension (`<package>LiveActivity`) to `project.pbxproj`, embeds it in the app and sets `NSSupportsLiveActivities`. The build lists what it added.
    - Files that exist are never overwritten, so the SwiftUI can be edited; a second build changes nothing. A project file that no longer matches the scaffold is left alone and the build says what to add by hand.
    - The extension needs its own App ID, `<app bundle id>.LiveActivity`, and signing profile before shipping.

### Commands

- Added `aimer update`: updates the CLI to the latest release.
- Added `aimer components`: manages the build environment, including the Aimer NDK.

## Fixes

- MCP: tracing logs now go to stderr. A warning or `--verbose` / `RUST_LOG` output on stdout corrupted the JSON-RPC stream and made clients drop the server.
- MCP: every Rust call after the first no longer hangs. Reads reported by the file watchers were treated as edits, which forced a full workspace reload after reading any `Cargo.toml` or `build.rs`, and re-indexed `.rs` files that had not changed. Reads and metadata-only changes are now ignored, and `build.rs` counts as a build script only next to a `Cargo.toml`.
- MCP: `get_project_metadata` now fails with `isError: true` when `cargo metadata` is unavailable, with the exit code, Cargo's message and an offline hint when the offline Cargo policy caused it.
- MCP: tool schemas are now portable. Optional parameters collapse to their single non-null type, and `preview_manifest_edit`'s `value` declares its TOML-compatible JSON types, so single-type dialects such as Gemini function declarations accept them. Tool names, argument names and required lists are unchanged.
- `aimer run` ignored `CARGO_TARGET_DIR` when it looked for what cargo had built, so a build into a directory of its own silently packaged a stale library from `target/`.
- The session's control connections no longer close while idle on macOS: they inherited the non-blocking mode of the listener, so an idle read failed at once.
- Fixed path separator handling (`/` and `\`) in the `components` command on Windows, Unix and other platforms.
- `aimer migrate` no longer wipes `builds/<platform>/`, which discarded signing settings, `Info.plist` and manifest edits, and custom icons. It merges the latest scaffold instead: missing files are added, generated code (`main.swift`, `AimerActivity.kt`, the Gradle wrapper) is refreshed, and edited files are kept and listed. `--force` replaces the edited files too. Documented in `docs/COMMANDS.md`.

## Improvement

- `inspect_file` text searches take `query`, matching `search_text`. `pattern` is still accepted as an alias.
- The app shows a badge, and draws where each injected pointer and finger is, for as long as an agent is controlling it, and only then: `aimer run`'s own connection never shows it. The MCP server tells the session an agent is there from its first tool that acts on the app until it exits, however idle it is in between, and a one-shot `aimer input` or `aimer screenshot` counts for four seconds after it. A debug build only.
- Input tools are documented in `docs/MCP.md` under "Driving the app", and listed in the `aimer-rust` skill.

## Changes

- MCP session tools `list_sessions`, `attach_session` and `detach_session` choose which live Aimer session a connection controls. The choice belongs to one connection, so agents sharing a workspace host do not move each other.
- An MCP connection now follows the workspace's live session automatically: with exactly one live session it attaches to it, even if it started after the server, and a session that ends is let go. `--attach` pins a session, and `detach_session` turns following off. Documented in `docs/MCP.md` under "Choosing the session".
- Input tools run one at a time as session operations, like `restart_project`, because they act on the running app and not on the workspace files.
- Removed the hot-reload crate (`aimer_hot_reload`). The shared configuration now lives in `aimer_config`.
- Added the `aimer_prendre` client dependency, used to send input to a running app. The session connects to the app as its launcher; agents get a connection of their own in the agent role.
- The session's status now reports `input_connected`, which says the app announced its input server and has been reached.
- Updated the CI/CD workflow.
