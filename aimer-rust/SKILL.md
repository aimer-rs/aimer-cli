# Aimer Rust

Use this workflow for Rust tasks in any workspace or crates selected in Aimer MCP.

## Rust source layout

- Keep every project-owned `.rs` file below 1,000 physical lines, including tests and documentation comments.
- When a file approaches the limit, move cohesive responsibilities into sibling modules and keep the parent module as a small facade.
- Name modules after the responsibility they own. Re-export only the items needed by callers; keep implementation details private.
- Keep tests beside the behavior they exercise, using child test modules or dedicated test files when that keeps source files within the line limit.

## Start with the requested task

- Do not scan or index the workspace just because an agent session started. Use the narrowest search or LSP operation that answers the current Rust task.
- Aimer Rust LSP tools start or reuse rust-analyzer and wait for indexing. Keep the call pending while progress is reported; do not treat an unfinished call as an empty result.
- If the user asks to work in a different workspace, use the Aimer MCP tool `start_lsp` with `project_path`. This changes the selected workspace for later Aimer Rust calls.

## Search and inspect

- Use the Aimer MCP tool `search_symbols` for symbol names or paths. It ranks exact matches ahead of fuzzy matches; add `kind` and a focused `limit` when useful. Rust kinds such as `trait` are accepted.
- Use the Aimer MCP tool `search_text` for literal text, comments, macro bodies, or other text that is not a symbol lookup. Narrow it with `file_glob`, case sensitivity, and `limit` as needed.
- Use the Aimer MCP tool `inspect_file` for selected source ranges and focused matches. Its default response has structured fields; use `format: "text"` for numbered source lines. Check `truncated_lines` before relying on long lines.
- Use the Aimer MCP tool `get_document_symbols` for a compact file outline with symbol names, kinds, and source lines. For implementation details, inspect the relevant source; the outline and hover are not substitutes for reading code bodies.
- Use the Aimer MCP tool `find_implementations` with `symbol_path` for a qualified trait path, or `file`, `line`, and `column` for a source position. Page with `limit` and `offset`; use `file_glob` and `include_tests` to refine results.
- Use the Aimer MCP tool `get_project_metadata` for a workspace map. Its default summary lists workspace packages, targets, and direct dependency names; request `detail: "full"` only when Cargo resolution metadata is needed.
- Completion returns up to 50 suggestions without documentation by default. Set a smaller `limit` for focused results or `include_documentation: true` when completion docs are needed.
- The Aimer MCP tool `get_diagnostics` returns diagnostics from the selected project and omits external Cargo registry files. Pass `file` to focus the result.
- Use the position-based LSP tools for definitions, declarations, type definitions, references, implementations, hover, signature help, call hierarchy, highlights, inlay hints, and macro expansion. Their lines and columns are 1-based, with columns measured in UTF-16 code units. Derive positions from source or returned locations; do not guess.
- If hover has no documentation, inspect the source doc comments. For dependency documentation, use Aimer's crate documentation tool when available.
- Summarize only the relevant result fields. Do not repeat a large JSON response unless the user asks for the raw result.

## Make Rust edits safely

- Use the current agent's file editing tools for ordinary code changes. Use Aimer's LSP edit tools when semantic rename, a specific code action, or formatting is the right operation.
- Treat results from the Aimer MCP tools `rename_symbol`, `get_code_actions`, `format`, and `preview_edit` as previews. Inspect each proposed diff and its validation report before using the Aimer MCP tool `apply_edit`. If a preview is stale, create a fresh one.
- Use the Aimer MCP tool `preview_edit` for precise local edits or project file creation/deletion. Supply project-relative paths and exact `old_text`/`new_text` replacements; each old anchor must match exactly once, and replacements in one file must not overlap. Do not use it for `Cargo.toml`; use the Aimer MCP tool `preview_manifest_edit` so Cargo validates the candidate.
- For rename results, surface possible unedited identifiers in `macro_rules!` bodies. Aimer does not add those candidates automatically; do not silently replace them or claim they were renamed.
- Do not apply a code action or formatting change unless it is part of the user's requested work.

## Diagnostics and checks

- Use `get_diagnostics` for diagnostics already known to rust-analyzer.
- The Aimer MCP tool `check` runs Clippy with all warnings denied. Use it when the user requests a check or the task requires that verification. Clippy must be installed; Aimer reports diagnostics but rust-analyzer does not expose Cargo's exit code. Cargo runs offline unless the user's Aimer configuration enables network access.
- Use the Aimer MCP tool `cargo_run` to build and run the selected project's default binary, a named `bin`, or an `example`. Pass app arguments through `program_args`; the foreground run has a bounded timeout. Its response keeps program output and filters Cargo build progress and compiler warnings.
